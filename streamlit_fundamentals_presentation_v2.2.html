Concept Discussion #1

Why is pure Python web development usually complex, and how does Streamlit simplify it?

Key Discussion Points:

  • Traditional stack requires Flask/FastAPI + HTML templates + JavaScript + CSS styling.
  • Streamlit converts plain Python data scripts into fully reactive web applications.
  • No REST APIs, route controllers, or DOM manipulation required.

What is Streamlit & Reactive Execution

1. Top-to-Bottom Execution

Every time a user interacts with a slider, button, or text box, Streamlit re-executes the entire Python script from top to bottom.

2. Variables as State

Widget values act directly as standard Python variables (`x = st.slider(...)`). No event handlers or callback registration required for simple apps.

3. Zero Frontend Code

Widgets rendering, WebSocket syncing, layout formatting, and CSS themes are entirely handled behind the scenes.

// EXECUTION FLOW MODEL
User interacts with Widget (e.g., Slider)
↓ Triggers Script Re-run
Python Script runs line 1 → N
↓ Renders UI Diff
Browser reflects updated outputs

Optimized by smart virtual DOM diffing over WebSockets.

Concept Discussion #2

How does Streamlit handle state updates when users interact with widgets like sliders and buttons?

Key State Principles:

  • Widget functions return their current front-end value directly into script variables.
  • A widget change triggers a full top-to-bottom re-run with updated return values.
  • Transient values (like `st.button` click status) reset to `False` on the subsequent re-run unless saved to `st.session_state`.

The Core Streamlit Philosophy

Session State & Caching

STATE PERSISTENCE

`st.session_state`

Persists variables across script re-runs during a active browser session. 

if "counter" not in st.session_state:
    st.session_state.counter = 0

if st.button("Increment"):
    st.session_state.counter += 1

st.write("Count:", st.session_state.counter)
PERFORMANCE OPTIMIZATION

`@st.cache_data`

Caches expensive database queries or ML model computations to avoid execution on every re-run. 

@st.cache_data
def fetch_heavy_dataset(query_id):
    # Runs ONLY when query_id changes
    df = pd.read_sql(...)
    return df

data = fetch_heavy_dataset(101)

Complete App Structure

Full Application Source Code:

import streamlit as st
import pandas as pd

st.set_page_config(page_title="Data Portal", layout="wide")

st.sidebar.title("Filters")
sample_size = st.sidebar.slider("Samples", 10, 100, 50)

st.title("Interactive Data Dashboard")
st.write(f"Displaying top {sample_size} records.")

data = pd.DataFrame({"ID": range(sample_size), "Score": [x*1.5 for x in range(sample_size)]})

col1, col2 = st.columns(2)
with col1:
    st.subheader("Data Summary")
    st.dataframe(data)
with col2:
    st.subheader("Distribution Chart")
    st.line_chart(data["Score"])

Best Practices & Common Gotchas

Recommended Patterns

Use Unique Keys for Dynamic Widgets

Always supply `key="unique_identifier"` when instantiating widgets inside loops.

Leverage `@st.cache_data` for Data Reading

Wrap SQL connections and file loading in cached functions to prevent re-fetching on every slider move.

Organize Code into Functions

Keep `main()` clean and break layout sections into modular helper functions.

Common Pitfalls

Expecting Button State to Persist

`st.button` only returns `True` for the single run right after clicking. Store state in `st.session_state` instead.

Heavy Computations Outside Caching

Placing raw ML predictions or API calls outside cached blocks will freeze your UI on every interaction.

Duplicate Widget Key Collisions

Re-using the exact same label without custom keys triggers a `StreamlitAPIException`.
